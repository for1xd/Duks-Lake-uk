# Нормалізація резидентів і приміщень

## Проблема
Модулі обліку (вода, сміття, паркінг, аркуші ДЗ «Комунальні», «Маркетинг», «Паркінг») зберігають назву резидента (`tenant`) і номер приміщення (`room`) як вільний текст. Через ручне введення й дані зі сканів один і той самий резидент записаний по-різному: латиницею й кирилицею, з помилками, зі старими назвами юросіб.

## Еталон (Source of Truth)
ДЗ OPEX за останній місяць (`dz/<YYYY-MM>_opex` → `rows`). Кожен рядок OPEX — еталонний резидент:

| Поле | Значення |
|---|---|
| `rid` | стабільний ідентифікатор: `<будинок>|<нормалізована назва>`, наприклад `1.2|fop-dryhanyk-vitali-sparkle` |
| `name` | назва з OPEX без змін |
| `bld` | будинок (`1.1`, `1.2`, `1.3`, `2`, `4`, `other` — «Інші резиденти» / «Окремо на локації») |
| `room` | приміщення з OPEX у єдиному вигляді (`101`, `106, 107, 108`) |

Сам аркуш OPEX нормалізацією не змінюється.

## Зв'язок «сирі дані → еталон»
1. **У кожному записі модуля** після міграції:
   - `tenant`, `room` — еталонні значення;
   - `rid` — посилання на еталонного резидента;
   - `nrRaw: {tenant, room}` — значення, які були до нормалізації (для аудиту й відкату);
   - `nrAt` — коли нормалізовано.
2. **Таблиця аліасів** `resolve/aliases` — ручні рішення, які алгоритм сам не вгадав:
   - `map[<id>] = {k, rid, name, bld, room, at, by}` — «ця сира назва = цей резидент» (наприклад, `Океанаріум` → `Світ Медуз`);
   - `ignore[<id>] = {k, at, by}` — «це не резидент» (технічний запис).
   - `k` — ключ аліаса: `<будинок або *>|<фонетичний ключ назви>`, тож рішення спрацьовує для всіх записів з такою назвою в усіх модулях і в майбутніх місяцях.

Порядок пошуку: таблиця аліасів → нечітке зіставлення.

## Алгоритм `normalizeResidentData(rawName, rawRoom, buildingId, ctx)`
Код — блок `NORM:BEGIN … NORM:END` в `index.html`.

1. **Очистка:** нижній регістр, без лапок, апострофів і спецсимволів; «3Ф» → «зф» (цифра 3 замість літери З).
2. **Службові слова відкидаються:** ФОП, ТОВ, ПП, «ор.», «ліч», «група» тощо.
3. **Фонетичний скелет латиницею:** кирилиця транслітерується, а схожі на слух написання зводяться до одного вигляду (c/k, ph/f, подвоєні літери, ц/ts → s). Тому `Claudspark` = `КлаудСпарк`, `ProCredit` = `ПРОКРЕДИТ`, `Сістерс` = `Sisters`.
4. **Оцінка схожості** з кожним еталонним резидентом будинку (0–1), береться найбільше з трьох значень:
   - Jaro-Winkler для назви, склеєної без пробілів (`Маменорі` = `Маме норі`), плюс бонус, якщо одна назва містить іншу;
   - покриття токенів, де рідкісні слова важать більше (IDF по еталону);
   - збіг «бренду» — рідкісного значущого слова (`Sparkle`, `Ігніс`).
   - Якщо збігся номер приміщення, додається +0.2.
5. **«А та Б»:** якщо в одному записі двоє резидентів одного приміщення, кожна частина зіставляється окремо.
6. **Без назви:** пошук за номером приміщення, завжди з ручною перевіркою.
7. **Рішення:**
   - **auto** — оцінка ≥ 0.86 і немає двох близьких кандидатів;
   - **review** — від 0.72 до 0.86 або неоднозначно;
   - **none** — нижче 0.72;
   - **skip** — технічні записи («загальнобудинковий», «Поверх 5 (вільно)», «Втрата…», «УК»).
8. **Приміщення** зводиться до одного вигляду (`кім. 107`, `офіс 107`, `№107` → `107`; списки й діапазони розгортаються). Якщо сирий номер входить до еталонних приміщень резидента (`107` із `106, 107, 108`), лишається конкретний номер; інакше береться еталонний.

Для паркінгу (і аркуша ДЗ «Паркінг») пошук іде по всіх будинках, бо будинок там — місце паркомісця, а не офіс резидента. Поле `room` там не чіпається: це номери паркомісць.

## Міграція (масове оновлення)
Facility відділ → **Нормалізація резидентів** (видно лише ролі Dev).

1. **Перевірка без запису (dry run):** записи групуються за сирою назвою, вкладки «Перевірити», «Автоматично», «Не знайдено», «Пропущено», «Уже правильні».
2. **Сумнівні записи:** «Підтвердити» пропозицію, вибрати іншого резидента зі списку або позначити «Не резидент». Ручні рішення зберігаються в таблицю аліасів.
3. **«Застосувати»:** записує еталонні значення (одне оновлення на документ) і зберігає старі в `nrRaw`.
4. **«Відкотити»:** повертає значення з `nrRaw`.

Повторний запуск безпечний: зіставлення завжди йде від `nrRaw`, а записи, які вже збігаються з еталоном, не змінюються.

`node tools/norm-check.js` проганяє рушій з `index.html` на контрольних прикладах.
